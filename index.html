PRESCOMART 平台概覽

多來源 → 單平台 → 多輸出 的統一電商 ERP

PRESCOMART 是一套統一商務管理平台（Unified Commerce ERP），將多個供應商來源整合到單一管理後台，再同步上架至多個銷售通路。目標是讓營運團隊在一個地方管理商品、訂單、財務、客服。

多來源整合 (Input)

供應商商品自動匯入、統一管理

PRESCOMART 的商品可以從多個來源匯入，每個來源透過對應的 Adapter 處理 API 格式差異，統一轉換後存入系統。

阿里巴巴 1688

透過 Source1688Adapter 串接 product-stream-api 服務，自動同步批發商品資料、價格、圖片。支援分頁載入，保留原始 API 回應供除錯。

供應商 REST API

通用 SourceApiAdapter，可自訂 endpoint URL、認證方式、欄位映射 (syncConfig)。一個 Adapter 支援任何提供 REST API 的供應商。

倉庫系統 API

與倉庫管理系統串接，取得即時庫存數量與物流資訊。支援 Webhook 接收庫存變動通知。

手動建立

後台直接新增商品，填寫品名、價格、SKU、圖片等資料。適合少量商品或無 API 的供應商。

來源同步機制

每個來源連線 (ProductSource) 都有獨立的同步設定與狀態追蹤。透過 ProductSourceLink 將外部商品映射到系統商品，支援雙向追蹤。

資料保留策略

  • 原始資料保留：每次同步的 Raw API Response 都會儲存，方便除錯與對帳
  • 欄位映射：透過 syncConfig 定義外部欄位 → 系統欄位的對應規則

財務模組

平台結算 (Settlements)

追蹤各平台應收的佣金支付。按期間分組，紀錄結算金額、已收款狀態。確保平台出帳金額與系統計算吻合。

供應商付款 (Supplier Payments)

管理應付供應商的貨款。支援外幣帳單 + 匯率轉換（ExchangeRate 模型）。追蹤發票編號、付款狀態。

財務交易 (Transactions)

所有金流進出的完整記錄：平台收入、供應商付款、運費支出、佣金、退款、調整項。每筆可關聯到訂單或結算單。

利潤分析 (Margins)

按商品、按訂單的利潤率分析。找出最賺錢和最虧錢的商品，輔助定價與採購決策。

客服系統

即時聊天 (Live Chat)

  • WebSocket (Socket.io) 即時雙向通訊
  • 自動顯示客戶資料 & 訂單歷史
  • 聊天分類路由：訂單問題、商品詢問、退換貨、配送、技術、其他
  • 客服可用狀態管理（在線 / 忙碌 / 離線）
  • 罐頭回覆 + 鍵盤快捷鍵
  • 滿意度評分系統

工單系統 (Tickets)

  • 優先度：LOW MEDIUM HIGH URGENT
  • 狀態流程：OPEN → IN_PROGRESS → WAITING_CUSTOMER → RESOLVED → CLOSED
  • 指派客服人員
  • 內部 / 外部訊息區分（內部備註不對外顯示）
  • 附件支援

訂單處理流程

不同通路的訂單如何進入系統、處理、出貨

PRESCOMART 接收來自多個銷售平台的訂單，每個平台的訂單格式、狀態碼、推送方式都不同。系統透過統一的訂單模型將差異抹平，讓營運團隊用同一套流程處理所有通路。

各通路訂單進入方式

博客來 Books.com.tw

  • 透過 API 定期拉取新訂單 (Pull)
  • 訂單包含：客戶資訊、商品明細、配送地址
  • 佣金率由平台連線設定自動帶入
  • 狀態回寫：出貨後推送物流單號回博客來

IOpenmall

  • Webhook 即時推送訂單 (Push)
  • 系統接收後自動建立訂單記錄
  • 支援測試 / 正式環境切換
  • 訂單狀態雙向同步

自營店面

  • 客戶在 /store/[slug] 下單
  • 訂單直接寫入系統資料庫
  • 無需額外同步，即時可見
  • 購物車 → 結帳 → 訂單確認

訂單同步機制

Pull 模式（定期拉取）

適用於不支援 Webhook 的平台（如博客來）。系統排程定期呼叫平台 API 抓取新訂單與狀態更新。透過 bulk-sync 端點批量同步。

Push 模式（即時推送）

平台透過 /api/webhooks/platforms 推送訂單事件。系統即時接收並處理，延遲最低。適用於支援 Webhook 的平台（如 IOpenmall）。

待開發功能 Roadmap

平台還需要什麼才能完整運作

以下是 PRESCOMART 要成為完整電商 ERP 還需要補齊的模組。按優先順序和相依性分為三個階段。

Phase 1 — 核心營運必備（高優先）

物流管理

目前缺乏完整的物流串接，是上線最大的缺口。

  • B2C 宅配：物流商 API 串接（黑貓、新竹物流等），自動產生託運單號、列印面單
  • B2 統一 / C2 統一：統一超商物流串接，支援店到店（C2C）及大宗寄倉（B2C）
  • 超商取貨：7-11、全家、萊爾富門市選擇 → 物流單建立 → 到店通知
  • 物流狀態追蹤：統一追蹤介面，自動更新訂單出貨狀態

金流 / 支付 — Payuni（PAYUNi）

串接 Payuni 統一金流平台，處理所有付款方式。

  • 信用卡：一次付清、分期付款
  • ATM 虛擬帳號：產生繳費帳號、到帳通知
  • 超商代碼繳費：產生繳費代碼
  • 付款狀態回調：Webhook 接收付款成功/失敗通知
  • 退款 API：整合退款流程

電子發票

台灣電商必備的發票管理功能。

  • 開立：訂單完成後自動開立電子發票（B2C / B2B）
  • 載具：支援手機條碼、自然人憑證、公司統編
  • 作廢 / 折讓：退貨時自動處理發票作廢或折讓單
  • 申報：與財務模組整合，輔助營業稅申報

庫存 / 倉儲管理 (WMS)

目前只有基本庫存欄位，需要完整倉儲管理。

  • 多倉庫：不同倉庫（楊梅、三峽等）獨立庫存
  • 進銷存：進貨、銷貨、調撥、盤點完整流程
  • 安全庫存：低於閾值自動警示或觸發採購建議
  • 批號 / 效期：食品類必備的批號追蹤與效期管理
  • 庫存同步：各平台即時扣庫存，避免超賣

Phase 2 — 營運效率提升（中優先）

退貨管理 (RMA)

完整的逆物流流程管理。

  • 退貨申請：客戶端或客服建立退貨單
  • 退貨原因分類：瑕疵、錯寄、不符預期等
  • 逆物流：安排取件或客戶寄回，追蹤退貨物流狀態
  • 驗收 & 入庫：退貨到倉後驗收，良品重新入庫
  • 退款觸發：驗收通過後自動走退款 + 發票折讓流程

帳務管理（進階）

在現有財務模組基礎上，補齊完整帳務功能。

  • 應收帳款：各平台結算金額追蹤、帳齡分析
  • 應付帳款：供應商付款排程、付款條件管理
  • 對帳：平台匯入帳單 vs 系統計算自動比對差異
  • 損益報表：按月/季/年、按平台/品類的損益匯總

罰款管理

電商平台常見的罰款追蹤。

  • 遲出貨罰款：超過平台規定出貨時限的罰款紀錄
  • 缺貨罰款：接單後無法出貨的罰款
  • 品質罰款：客訴率過高、退貨率過高的罰款
  • 罰款統計：按平台、按月匯總，計入成本分析
  • 預警機制：接近出貨期限自動提醒避免罰款

客戶中心 / CRM — Uniopen

統一客戶資料管理，提升回購率。

  • 客戶合併：跨平台的同一客戶資料合併識別
  • 購買歷史：完整的跨通路消費記錄
  • 客戶分群：RFM 分析、標籤系統
  • 會員等級：累積消費 / 頻率決定等級與權益
  • Uniopen 整合：串接 Uniopen 客戶中心平台

Phase 3 — 規模化 & 合規（長期）

供應商合約管理

  • 合約建立：記錄合約期間、付款條件（月結30/60天等）、最低訂購量
  • 價格協議：階梯定價、促銷期間特價、匯率連動
  • 績效考核：交貨準時率、品質合格率、缺貨率
  • 到期提醒：合約即將到期自動通知續約
  • 文件管理：合約 PDF 上傳、版本管理

平台合約管理

  • 合約條款：佣金率、結算週期、罰款條款、保證金
  • 費用結構：上架費、月費、成交手續費拆分記錄
  • SLA 追蹤：出貨時限、回覆時限、退貨處理時限
  • 自動核對：平台收費 vs 合約條款自動比對異常
  • 多平台比較：各平台利潤率、費用率橫向對比

什麼是 Vibe Coding？

用自然語言驅動的開發方式

Vibe Coding 不是「讓 AI 寫所有程式」，而是用 AI 作為溝通媒介，讓 PM 和 IT 都能快速產出「看得見的東西」來對齊需求。

傳統開發 vs Vibe Coding

傳統開發流程

  1. PM 花 3 天寫 PRD 文件
  2. IT 花 1 天讀文件、開會討論
  3. IT 花 1-2 週開發
  4. PM 看到成品：「不是這樣...」
  5. 來回修改 2-3 輪
  6. 整個週期：3-6 週

核心問題：文字描述永遠有落差。PM 腦中的畫面和 IT 理解的畫面，很難完全一致。

vs

Vibe Coding 流程

  1. PM 用 Claude 做出原型畫面（半天）
  2. IT 看到畫面，立刻理解需求
  3. IT 用原型展示技術限制
  4. 雙方對著畫面討論、快速對齊
  5. IT 用 Claude 快速實作
  6. 整個週期：3-7 天

核心改變：用「看得見的東西」取代文字溝通。雙方對著同一個畫面討論，誤差趨近於零。

關鍵思維轉變

原型 > 文件

一個可互動的原型畫面，比 10 頁 PRD 更能傳達需求。AI 讓做原型的成本降到趨近於零。

展示 > 解釋

「為什麼這樣不行」用說的很難懂。但做一個 demo 讓對方自己看到問題，秒懂。

迭代 > 一次到位

不追求第一版就完美。先做出來、看到問題、快速修正。每次迭代只要幾分鐘。

PM 的角色

理解使用者、做出原型、定義 Input/Output

PM 的核心工作是用 Claude 做出「有完整元素的畫面原型」——不需要實際功能，但畫面上要有所有使用者會看到和操作的元素。

PM 負責的事

  • 理解使用者的真實工作流程——他們現在怎麼做？哪裡最痛？
  • 定義 Input：使用者會輸入什麼資料？資料從哪裡來？什麼格式？
  • 定義 Output：最終要產出什麼？Excel？PDF？網頁畫面？給誰看？
  • 排版與資訊架構：頁面上要有哪些欄位、按鈕、表格？
  • 用假資料填充：讓原型看起來像真的在運作
  • 標注互動意圖：點了這個按鈕預期會發生什麼？
  • 考慮邊界情況：空的時候長怎樣？載入中？出錯了？
  • 資訊安全把關：哪些資料是敏感的？誰能看到什麼？權限怎麼分？
  • 準備 API 串接資料：找到第三方的 API 文件、申請帳號、整理基本連線資訊（endpoint、key、規格書），交給 IT 實作

PM 不用管的事

  • 資料庫怎麼設計（IT 的事）
  • API 怎麼串接（IT 的事，但 PM 要準備文件和帳號）
  • 效能、可維護性（IT 的事）
  • 程式碼品質或架構選擇
  • 部署和基礎設施

重點：PM 的原型不需要「能動」，只需要「看起來對」。但畫面上的每個元素都要有——缺了元素，IT 就不知道要做什麼。

PM 做原型的步驟

1. 訪談使用者
→
2. 定義 I/O
→
3. 用 Claude 產出原型
→
4. 加假資料
→
5. 交付 IT

PM 最大的價值是「理解使用者的工作流程」——使用者在什麼情境下用這個功能？手邊有什麼資料？最後要產出什麼給誰？
這些是 AI 無法替代的，因為 AI 不認識你的使用者。

PM Prompt 範例

給 Claude 的 Prompt： 我要做一個採購單頁面的原型。使用者是採購人員。 他們的工作流程： 1. 從 Google Sheets 看到商品清單 2. 選擇要採購的商品，填寫數量和日期 3. 產出供應商訂單 Excel、倉庫單 Excel、嘜頭標籤 請做出一個頁面，左邊是商品表格（含搜尋、篩選）， 右邊是全域欄位（訂單日期、採購單號、到貨日期）， 上方有三個匯出按鈕。用假資料填充 10 筆商品。

IT 的角色

技術把關、用原型溝通問題、實作完整功能

IT 不只是接到需求就寫 code。IT 要能用原型向 PM 和使用者「展示問題」，而不是只用文字解釋。

IT 負責的事

  • 評估 PM 原型的技術可行性——哪些能做、哪些有風險
  • 用原型展示「為什麼不行」——做一個 demo 讓 PM 自己看到
  • 提出替代方案的原型——不只說不行，要展示更好的做法
  • 設計資料結構 & API——確保後端能支撐前端需求
  • 用 Claude 快速實作——善用 AI 加速開發
  • 效能、安全性、可維護性——這是 IT 的專業守備範圍

IT 不該做的事

  • 只用文字解釋「為什麼不行」
  • 直接說「做不到」卻不給替代方案
  • 自己假設使用者需求（那是 PM 的工作）
  • 閉門造車、做完才給 PM 看

傳統 IT 常犯的錯：花大量時間解釋技術限制，PM 還是聽不懂。
解法：做一個 demo 讓 PM 自己體驗問題。

實際案例：IT 如何用原型溝通

Step 1 — PM 給了原型
「表格直接顯示所有 5000 筆商品，不需要分頁」
Step 2 — IT 做了 demo
用 Claude 快速做一個載入 5000 筆的頁面 → 開啟後等 3 秒才看到內容，捲動卡頓
Step 3 — IT 做了替代方案
做另一個用「虛擬捲軸 + 搜尋」的版本 → 秒開、捲動流暢
Step 4 — PM 自己比較
兩個版本並排，PM 自己操作後立刻理解為什麼需要虛擬捲軸。不需要解釋任何技術細節。

「讓 PM 自己看到問題」比「跟 PM 解釋問題」有效 100 倍

完整協作流程

PM × IT × Claude 的三方協作

階段PM 做的事IT 做的事產出物
1 需求 訪談使用者、觀察工作流程、定義 Input / Output — 使用者故事 & I/O 規格
2 原型 用 Claude 做出視覺原型（有完整元素、假資料） — HTML 原型畫面
3 技術評估 說明流程意圖、使用者情境 評估技術可行性、識別風險 可行性分析
4 問題溝通 體驗 IT 做的問題 demo 用原型展示問題、提供替代方案原型 調整後的設計共識
5 開發 定期 review、給回饋 用 Claude 實作、漸進式交付 可用的功能
6 迭代 收集使用者回饋、提出改進 快速修改、部署更新 持續改善的產品

適合 Vibe Coding 的場景

很適合

  • 內部工具 & 後台系統 — 使用者明確、需求可控
  • 資料處理 / 匯出工具 — Input/Output 明確
  • 原型驗證 & MVP — 速度最重要
  • CRUD 頁面 — 模式化、AI 擅長
  • Excel / 報表生成 — 格式規範明確

要注意

  • AI 生成的 code 需要 review — 不能盲信
  • 複雜商業邏輯 — 仍需人工設計
  • 安全性 — AI 可能寫出有漏洞的 code
  • 需求不清 = AI 也做不好 — 垃圾進垃圾出
  • 不是「不需要工程師」 — 是讓工程師更有效率

Vibe Coding 不是取代人，是讓 PM 和 IT 都能用「看得見的東西」溝通

挑戰 & 經驗總結

AI 開發的真實面貌

遇到的主要挑戰

挑戰原因解法
Amplify SSR 環境變數不生效 Lambda runtime 不讀 .env 檔案 Pre-build 寫入 .env.production → next.config 打包進 bundle
欄位名稱含換行 / 特殊空白 Google Sheets 欄位標題有 \n、NBSP Strip 所有空白字元後再做欄位比對
同名欄位出現兩次 Sheet 設計：Column A 和 Column C 都叫「i預購品號」 程式碼明確取「第二次出現」的欄位索引
1000+ 商品表格卡頓 太多 DOM 節點導致渲染緩慢 使用 react-window 虛擬捲軸，只渲染可視區域
嘜頭格式精確度 Excel 合併儲存格 + 特定字型 + 符號要求 逐格設定 xlsx-js-style，3 次迭代才達到正確格式
日期自動填入導致錯誤 使用者反映自動填入的日期常常是錯的 移除自動填入，改為手動輸入

迭代類型分析

修正類 — 40%

欄位映射錯誤、環境變數問題、日期格式、空白字元。這類問題是 AI 無法事先預知的業務細節——只有看到真實資料才會發現。

新功能 — 35%

訂單管理、多試算表、製造商篩選。使用者用了之後才發現需要的功能——這就是為什麼要快速出第一版。

UI 優化 — 25%

欄寬調整、色彩標記、展開/收合、精簡版面。讓工具從「能用」變成「好用」的最後一哩路。

這個案例驗證了什麼？

Vibe Coding 的成功要素

  • Input/Output 非常明確 — Google Sheets → Excel，沒有模糊空間
  • 格式規範具體 — 嘜頭字型、顏色、欄位都有精確要求
  • 漸進式開發 — 先能用，使用者回饋後再改
  • 快速回饋循環 — 部署後使用者立刻測試、立刻回報

AI 開發的真實面貌

  • 40% 時間在修正 — 業務規則 AI 猜不到，只能靠迭代
  • 環境問題仍需人工 — Amplify SSR 的坑不是 AI 能預見的
  • Excel 格式靠迭代 — 看到 output 才知道對不對
  • 2 天完成 = 傳統 1-2 週的工作量

AI 是加速器，不是替代品。好的需求定義 + AI 工具 = 10 倍效率。
